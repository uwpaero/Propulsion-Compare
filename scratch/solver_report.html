1. Overview & Scope

propselect selects and ranks electric motor + propeller combinations for a fixed-wing aircraft against a takeoff-distance requirement and/or a cruise (steady, level-flight) requirement. For each candidate (a motor, a propeller, and a motor count, direct drive only), it solves the coupled motor/propeller electrical-mechanical operating point — across an airspeed sweep for takeoff, or at a single thrust-equals-drag equilibrium for cruise — and scores the result against a set of filters (tip Mach, current, power, efficiency, distance or endurance).

The physics core (propselect/core/) has zero GUI dependencies and is fully scriptable headlessly; the GUI and CLI are thin front ends over the same functions documented here.

5. Atmosphere Model

ISA (troposphere, <11 km) with an optional offset, or direct entry of density and temperature. Source: core/atmosphere.py.

T(h) = T0 + ΔISA − L·h (ISA temperature) P(h) = P0 · (1 − L·h/T0)^(g0/(R·L)) (ISA pressure) a = √(γ·R·T) (speed of sound) ρ = P / (R·T) (ideal gas density)
ConstantValueSource
γ (air)1.4ratio of specific heats, dry air
R (air)287.05 J/(kg·K)specific gas constant, dry air
g₀9.80665 m/s²standard gravity
T₀, P₀288.15 K, 101325 PaISA sea-level reference
L0.0065 K/mISA tropospheric lapse rate

The "field elevation + OAT" mode uses the ISA pressure profile at the given elevation but the actual measured temperature for density (standard density-altitude convention) rather than the ISA-standard temperature at that altitude, since OAT is normally known directly.

6. Battery Model

Model A — internal resistance (default)

V_ocv,pack(SoC) = V_ocv,cell(SoC) · series [V_ocv,cell via PCHIP of an OCV table] R_pack = R_cell · series / parallel V_terminal(I) = V_ocv,pack(SoC) − I · R_pack

Model B — measured curve

Direct PCHIP interpolation of a user-supplied loaded V-vs-I table; SoC is not used (the curve already reflects whatever charge state it was recorded at).

Both models clamp queries outside their data range and return a warning rather than extrapolating silently.

SoC bookkeeping. soc_from_capacity_used(soc0, capacity_Ah, Ah_used) = soc0 − Ah_used/capacity_Ah, linear discharge tracking. No temperature, C-rate-dependent-resistance, or nonlinear capacity-fade effects are modeled.

7. Motor Model

Direct drive only — the motor shaft and the propeller shaft are the same shaft (n = nmotor = nprop, Q = Qmotor = Qprop). No gearbox is modeled.

K_t = (60/2π) / K_v = 9.5493 / K_v [N·m/A] Q = K_t · (I − I₀) V_back-emf(n) = 60·n / K_v [n in rev/s] η_motor = Q·ω / (V·I), ω = 2πn

8. Propeller Model

J = V / (n·D) T = C_T(J) · ρ · n² · D⁴ [N] P = C_P(J) · ρ · n³ · D⁵ [W] Q = C_P(J) · ρ · n² · D⁵ / (2π) [N·m]

Interpolation: CT(J) and CP(J) come from tabulated test data (APC .dat, UIUC, or CSV), interpolated with scipy.interpolate.PchipInterpolator — a monotone cubic that cannot overshoot between data points. Below the table's J range the lowest table value is held (flagged below_table_range). At and beyond the zero-thrust crossing point, CT is clamped to zero and CP is held at its value at that crossing (flagged beyond_zero_thrust) — the interpolator can never be asked to produce negative power.

PCHIP is monotonicity-preserving, not resolution-inventing. If a source table has two consecutive J rows with the identical (rounded) CP, PCHIP is mathematically required to be exactly flat between them — it computes zero derivative at both knots to avoid overshoot, and a Hermite cubic with equal endpoints and zero end-slopes is the constant function. This is identical to what linear interpolation would give in that same interval. A flat run of solved n(V)/I(V) across a narrow J range is therefore evidence of a coarse/rounded source table (APC files publish CP to 4 decimals), not a solver defect.

Parametric fallback (no tabulated data): linear CT decay from a static value to zero at J = 0.9·(pitch/D), constant CP. Any candidate using it is flagged low_confidence_parametric throughout the UI and results.

Import validation (data/loaders.py): APC files are cross-checked by recomputing thrust from the parsed CT at ρ=1.225 kg/m³ and comparing to the file's own thrust column; a >2% mean mismatch rejects the import. Multiple RPM blocks in one file are checked for CT(J) agreement (±5%); if they disagree beyond that (a Reynolds-number effect at low RPM), the loader uses the single block nearest an expected operating RPM rather than blending mismatched-Reynolds data.

9. Coupled Operating-Point Solver

Source: core/operating_point.py. Solved as a 1-D root find in propeller speed n, not a 2-D fsolve over (n, I) — the torque/current relationship is algebraically substituted out first, which is both faster and immune to the false/nonsense convergence a naive 2-D solve is prone to.

For a trial n at a given V:

1. J = V / (n·D) 2. (C_T,C_P) = interpolate(J) 3. Q_prop = C_P·ρ·n²·D⁵ / (2π) 4. I = I₀ + Q_prop / K_t [per motor] 5. V_batt = battery.terminal_voltage(motor_count·I, SoC) 6. residual(n) = V_batt − I·(R_motor+R_esc) − 60·n/K_v

Root-found with scipy.optimize.brentq over n ∈ [nmin≈10⁻⁵, nno-load], where nno-load = Kv·Vbatt(I=0) / 60. The bracket is sign-checked before calling brentq; if there is no sign change, the candidate returns a structured OperatingPointFailure with a diagnostic reason (insufficient voltage, mismatched Kv/prop, excess resistance, etc.) — never a bare exception, never a silently-wrong number.

V_batt(I) here is the loaded terminal voltage, which for the internal-resistance battery model already nets out I·Rinternal internally. Rmotor+Resc is added on top of that (not Rinternal a second time) — this is what keeps the residual equivalent to "Vocv − I·(Rmotor+Resc+Rinternal) = back-emf" without double-counting the battery's own resistive drop, and it generalizes correctly to the measured-curve battery model, which has no separate R to extract.

Once converged: T and Pshaft are computed from the coefficients and aggregated by motor count (see §10); ηmotor = Q·ω/(V·I); ηprop = T·V/Pshaft (defined as 0 at V=0, since useful propulsive power is zero at zero airspeed regardless of thrust).

10. Multi-Motor Extension

motor_count identical motor+prop+ESC units are assumed to share one pack and split the load symmetrically — each solves to the same per-motor operating point (self-consistent, since the motors are identical and see the same bus voltage), and the pack sees motor_count times the per-motor current.

QuantityScaling
Current (I)per-motor; solved directly from motor circuit equation
Pack current (Ipack)= motor_count × I — this is what drives battery voltage sag and SoC depletion
Thrust, Pshaft, Pelecaggregate = motor_count × per-motor value
ηmotor, ηpropper-motor ratios, unaffected by count (numerator and denominator scale identically)
Why per-motor current filters and pack current filters are separate. ESC/motor continuous-current ratings are per-unit limits; a battery C-rate limit is a pack-level limit on the sum of every motor's current. Conflating them (as a single-motor tool naturally can, since the two coincide when motor_count=1) silently misrepresents utilization once motor_count>1 — propselect reports current_per_motor and current_pack as two distinct filters for exactly this reason.

11. Ground-Roll Integration

F_net(V) = T(V) − D(V) − μ·(m·g − L(V)) D(V) = 0.5·ρ·V²·S·C_D,ground L(V) = 0.5·ρ·V²·S·C_L,ground ds = m·V·dV / F_net(V) dt = m·dV / F_net(V)

Integrated with the trapezoidal rule on a fixed dV grid (default 0.1 m/s). If Fnet(V) ≤ 0 anywhere, distance is reported as infinite, along with the airspeed where it went non-positive and the force deficit at that point — a diagnostic, not just a failed number.

Optional ground-effect correction

Φ = (16h/b)² / (1 + (16h/b)²) C_D,ground = C_D0 + Φ·C_L² / (π·AR·e) [AR = b²/S, derived]

Off by default. When enabled, CD0 (the user's "ground-roll CD" input) is treated as the parasite baseline and the induced term above is added on top.

SoC feedback (two-pass fixed point)

Pack voltage sag depends on SoC, which depends on cumulative current draw, which depends on the (still unknown) time-of-flight, which depends on thrust, which for the internal-resistance battery model depends on SoC — circular. Solved with two passes: the first assumes constant initial SoC to get an approximate current/time profile; the second re-solves every operating point against the SoC sag implied by that profile. SoC sag over one takeoff run is small enough that this converges to a good approximation without an inner iterative solve per grid point.

12. Cruise (Steady Level Flight)

Source: core/cruise.py. Cruise is a single equilibrium condition, not an integration: thrust must equal drag at one airspeed, with the aircraft in steady, unaccelerated, level flight (L=W). There is no time-of-flight to integrate and no diagnostic sweep grid — one candidate at one cruise velocity produces exactly one operating point.

C_L = 2·m·g / (ρ·V²·S) C_D = C_D0,cruise + C_L²/(π·AR·e) T_req = D = 0.5·ρ·V²·S·C_D

CD0,cruise is a separate input from the ground-roll CD0 (§11) — the ground-roll value describes a gear-down, ground-proximity configuration and does not represent a clean-configuration cruise condition. Mass, wing area, span, and Oswald efficiency are reused directly from the same AircraftConfig as takeoff (§11); the ground-only fields (μ, CL,ground, wheel height, ground effect) are simply unused here.

Thrust-matched propeller speed

The coupled operating-point solver (§9) has no throttle knob — it solves the single full-throttle (WOT) condition. Cruise reuses it for two purposes: as the search bound and as the feasibility ceiling.

1. WOT = solve_operating_point(V, ...) [§9, full throttle] 2. if WOT.thrust < T_req: infeasible [cannot sustain this V] 3. find n ∈ [n_min, WOT.n] such that: motor_count · C_T(J(n))·ρ·n²·D⁴ = T_req [brentq root-find, T(n) at fixed V]

This works because thrust depends only on n and V, not on throttle setting, while the motor's torque/current relation Q=Kt·(I−I₀) (§7) holds at any throttle — so once n is thrust-matched, current follows directly with no throttle model needed at all:

Q_prop = C_P(J)·ρ·n²·D⁵/(2π) I = I₀ + Q_prop/K_t [per motor, throttle-independent] V_required = I·(R_motor+R_esc) + 60·n/K_v [motor terminal voltage needed] throttle = V_required / V_batt(I_pack, SoC)
Throttle model: linear/resistive ESC, not a switching buck converter. Partial throttle is modeled as the ESC dropping the excess voltage (Vbatt − Vrequired) resistively, so pack current equals motor current exactly as at WOT (Ipack = motor_count × I, no step-down). This is a conservative (pessimistic) assumption for partial-throttle battery draw and endurance — a real switching ESC draws less pack current than motor current at partial throttle (Ipack ≈ duty × Imotor for an ideal lossless buck). Upgrade path if endurance estimates need to be tighter: model duty = Vrequired/Vbatt explicitly and scale Ipack by it.

Endurance and range

endurance = SoC₀ · capacity_Ah / I_pack · 3600 [s] range = endurance · V_cruise [m]

Endurance is reported only when the battery model exposes a finite capacity_ah (the measured-curve model may not).

Cruise envelope (for plotting)

cruise_envelope() re-solves the equilibrium above at each airspeed in a caller-supplied list — it is a thin wrapper (dataclasses.replace on v_cruise_m_s, no new physics) used by the GUI's Cruise Detail tab to plot how thrust, throttle, current, and efficiency vary across a speed range around the configured cruise velocity, since a single candidate otherwise yields only one point.

13. Closed-Form Quick Estimate

A single-point, constant-acceleration estimate shown live on the Aircraft & Requirement tab — not a substitute for the full integration, but immediately shows which term (inertia, drag, friction) dominates the requirement as inputs change.

V_eff = V_T / √2 q̄ = 0.5·ρ·V_eff² T_req ≈ m·V_T²/(2s) + q̄·S·C_D + μ·(m·g − q̄·S·C_L) (inertia) (drag) (friction)

15. Momentum-Theory Cross-Check

T_static = FM · (2·ρ·A)^(1/3) · P_shaft^(2/3), FM ∈ [0.4, 0.75]

Computed per-motor at the static (V=0) point and compared against the solved static thrust; if outside the band, a warning is attached to the candidate ("check propeller data and units") — it is a data/unit sanity check, not a hard filter, since real propellers legitimately scatter around ideal actuator-disk theory. For multi-motor candidates, aggregate thrust/power are divided back to per-motor values first: because T ∝ P^(2/3) is a nonlinear (not proportional) relationship, checking totals directly would bias the band by motor_count^(1/3).

16. Assumptions & Limitations

Quasi-steady propulsion. Motor and propeller are assumed to reach their equilibrium operating point instantly at every airspeed step (or, for cruise, at the single solved equilibrium) — no rotational inertia, spool-up lag, or throttle transient is modeled.
No unsteady aerodynamics; only the wing sees ground effect. The optional ground-effect correction reduces wing induced drag near the runway (takeoff only); the propeller's own thrust/power coefficients are not corrected for proximity to the ground.
Rigid, flat, level runway; one rolling-friction coefficient for the entire roll (surface presets: pavement 0.02, hard turf 0.05, short grass 0.08, mown grass 0.10, tall grass 0.15). No wind, no gusts, no crosswind. (Takeoff only — cruise has no runway.)
Symmetric multi-motor. N identical units, perfectly balanced load sharing, one shared pack/bus voltage. Asymmetric installations (different motors/props per position) are not modeled. Applies identically to cruise (§12).
Battery. The internal-resistance model is linear with SoC-only voltage sag — R_internal is a single constant, not itself SoC- or temperature-dependent, so the model cannot show the resistance rise (and worse sag) real packs exhibit late in discharge or when cold. No thermal effects, no capacity fade. The measured-curve model captures real nonlinearity but is frozen at whatever SoC it was recorded at. Deliberate scope choice, not an oversight: a full electrochemical model (e.g. PyBaMM) would replace an O(µs) algebraic lookup with a per-point PDE solve, which is incompatible with sweeping dozens-to-hundreds of candidates interactively; an SoC-indexed resistance table (same PchipInterpolator pattern as the OCV table) is the identified upgrade path if this fidelity gap matters.
Cruise throttle model. Partial throttle is modeled as the ESC dropping excess voltage resistively rather than as a switching buck converter — pack current equals motor current at any throttle setting, not duty × I_motor. Conservative (pessimistic) for partial-throttle endurance/range estimates (§12).
Propeller data validity. Tabulated CT/CP curves are assumed valid across the solved J range at whatever Reynolds number the operating point implies. The loader explicitly flags (rather than silently accepts) RPM-block disagreement from real Reynolds effects at low RPM (§8).
Interpolation resolution. PCHIP cannot invent precision the source table doesn't have — flat regions in coarse or rounded published propeller data (e.g. APC's 4-decimal CP) appear as genuinely flat solved n(V)/I(V), not solver error (§8).
Ground roll ends at VT (rotation/target speed), not the full liftoff transition, flare, or climb-out. Cruise is evaluated only at the configured cruise velocity/altitude, not as a full mission profile (climb, descent, reserve).
No CG shift, aeroelastic effects, or propeller wake interference between multiple motors on one airframe.
